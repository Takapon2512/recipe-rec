# S-007 パスワードリセット

**URL**: `/password-reset`
**Figma**: [{TBD}]({TBD})

### 🎯 目的

- パスワードを忘れた既存ユーザーが、メール宛のコードを使って自力でパスワードを再設定できるようにする
- 「メール入力 → コード送信 → コード+新パスワード入力 → 完了」という2ステップを **1画面の中でステップ表示** することで、画面遷移を増やさずに迷わせない
- ユーザー列挙攻撃を防ぐため、登録の有無に関わらず常に「コードを送信した」という応答を返す設計にする
- S-005 ログイン画面からの遷移時にメールアドレスを引き継ぐことで、二度入力させない

### 📋 構成要素

#### ヘッダー（上部固定、56px / 共通仕様準拠）

| パーツ | 配置 | 内容 |
|-------|------|------|
| `←` 戻る | 左 | S-005 ログインへ戻る |
| タイトル | 中央 | `パスワードをリセット` |
| (右はアイコンなし) | 右 | - |

> 認証系画面のため BottomNavigation は非表示。

#### ステップインジケーター（ヘッダー直下）

2ステップの進捗を可視化：

```
①メール送信 → ②新パスワード設定
   ●○                ○○
```

- text/caption (12px)、`color/text-secondary`、現在地のみ `color/primary` で強調
- ステップ間は `→` で接続
- 下に余白16px

> **設計判断**: S-004 のステップインジケーターと同じビジュアル言語を使い、認証系フローでの一貫性を保つ。

## ステップ2: コード入力 + 新パスワード設定

`step = "confirm"` のときに表示。同一画面内でブロックを差し替える（URLは変えない）。

#### イントロブロック

- 大きめの見出し: `新しいパスワードを設定`（h1相当、24px / 700）
- サブテキスト（複数行可）:
  - 1行目: `下記のメールアドレスに6桁のコードを送信しました。`
  - 2行目: `<user@example.com>`（送信先メールアドレス、`color/text-primary`、500、改行で目立たせる）
- メールアドレス右に小さく `変更` リンク（タップでステップ1に戻る、後述の確認ダイアログあり）
- 下に余白24px

#### コード入力フィールド

S-003 と同じスタイルの6マス分割UI：

```
┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐
│  │ │  │ │  │ │  │ │  │ │  │
└──┘ └──┘ └──┘ └──┘ └──┘ └──┘
```

| 項目 | 値 |
|------|-----|
| マスのサイズ | 48×56px |
| マス間の間隔 | 8px |
| フォント | 24px / 600、中央寄せ |

| 入力制約 | 半角数字のみ、1マス1文字 |

> **設計判断**: S-003 / S-004 と同じ6マスUIにすることで、ユーザーがすでに学んだ操作パターン（自動フォーカス移動・ペースト分配）をそのまま使える。

#### 再送セクション（コード入力欄の下）

- `コードを再送`（リンク、`color/primary`、text/body）
  - 直後は60秒間タップ不可（S-003 と同じ方針）
  - 残り秒数があるときは `コードを再送（あと45秒）` のように表示、`color/text-secondary`
- `メールが届かない場合は、迷惑メールフォルダもご確認ください。`（text/caption、`color/text-secondary`）

#### 新パスワード入力フィールド

| フィールド | 入力UI | 仕様 |
|-----------|-------|------|
| 新しいパスワード ※ | Input `text`（type=password、目アイコンで表示切替） | 8文字以上、英大文字・小文字・数字・記号を含む、`autocomplete=new-password` |
| 新しいパスワード（確認用） ※ | Input `text`（type=password、目アイコンで表示切替） | 上のパスワードと完全一致、`autocomplete=new-password` |

##### パスワード強度・要件チェックリスト

S-002 と同じく、パスワード入力欄の直下にリアルタイムで要件を可視化：

```
□ 8文字以上
□ 英大文字を含む
□ 英小文字を含む
□ 数字を含む
□ 記号を含む
```

- 入力に応じて満たした要件は `✓`（`color/success`）に切り替わる
- すべて満たすまで「リセット」ボタンは非活性
- フォント: text/caption (14px)

> **設計判断**: S-002 サインアップと同じチェックリストを使い、Cognito のパスワードポリシー（design.md §1.1 準拠）を視覚的に伝える。新規パスワードを決める場面なので、S-005 ログインと違ってチェックリストは出す。

#### ボトム固定フッター（72px / 共通仕様準拠）

- `パスワードをリセット` ボタン（Button `lg` primary、横幅100%、高さ48px）
  - コード6桁・新パスワード・確認用パスワードすべてのバリデーションを満たすまで非活性
  - タップでローディング状態へ（スピナー表示、入力ロック）

## ステップ3: 完了画面（成功表示）

`step = "done"` のときに表示。短いサクセス画面。

#### 構成

- 中央寄せ:
  - 成功アイコン（チェックマーク、48×48px、`color/success` 円背景に白）
  - 見出し: `パスワードをリセットしました`（h1相当、24px / 700）
  - サブテキスト: `新しいパスワードでログインしてください。`（text/body、`color/text-secondary`）
- 下に余白32px

#### ボトム固定フッター

- `ログインへ` ボタン（Button `lg` primary、横幅100%、高さ48px）
  - タップで S-005 へ遷移（メールアドレスを state で引き継ぐ）

> **設計判断**: 自動でログイン状態にはしない。Cognito の `ConfirmForgotPassword` API は JWT を返さないため、別途 `InitiateAuth` を呼ぶ必要があるが、「リセット直後はあえて再ログインさせる」ことで「パスワード変更が確かに反映された」という安心感を与える。また、攻撃者がアカウント乗っ取りを完遂しても、即座にホームに入れない一段ハードルを作る意味もある。

### 🔄 インタラクション

#### バリデーションのタイミング

S-002 / S-005 と同じ方針：

- **初回フォーカス前はエラー表示しない**
- blur 以降からインラインバリデーション開始
- パスワード要件チェックリストだけは例外で、入力開始と同時にリアルタイム更新

#### バリデーションルール（クライアント側）

| 項目 | ルール | エラーメッセージ例 |
|------|--------|------------------|
| メールアドレス | RFC準拠メール形式、1〜254文字 | 「メールアドレスの形式が正しくありません」 |
| 確認コード | 半角数字6桁 |（6桁揃うまでボタン非活性、入力中はエラー出さない） |
| 新パスワード | 8文字以上、英大小・数字・記号を含む | 「パスワードは8文字以上で、英大小・数字・記号を含めてください」 |
| 新パスワード確認 | 上のパスワードと一致 | 「パスワードが一致しません」 |

#### コード入力のキー操作

S-003 と同じ挙動：

- 1文字入力すると次のマスにフォーカスが自動で移動
- Backspace で前のマスに戻る（空のマスでBackspace押下時、前のマスの値をクリア）
- 6桁ペースト時に各マスに自動分配（クリップボードから 6桁の数字をペーストすると分配）
- 数字以外の入力は無視

#### パスワード表示切替

- 各パスワード欄の右端に目アイコン（24×24px）
- タップで `type=password` ↔ `type=text` を切替
- 確認用パスワードも独立して切替可能（互いに連動しない）

#### ステップ1のAPI呼び出し（コード送信）

```
[コードを送信] タップ
    ↓
Cognito SDK forgotPassword({ Username: <email> })
    ↓
成功 / "UserNotFoundException" のどちらでも:
    ↓
ステップ2へ画面遷移（state内の step を "confirm" に切り替え）
+ 再送タイマーを60秒開始
失敗（ネットワーク等）: 上部にエラーバナー表示
```

> **設計判断メモ（セキュリティ）**: `UserNotFoundException` が返ってきた場合も、UI上は **成功と同じ挙動**（ステップ2へ遷移）にする。これにより、「このメールアドレスが登録されているか」を攻撃者から隠す（ユーザー列挙攻撃対策、S-005 と同じ方針）。Cognito 側で `Prevent user existence errors` を有効化することでサーバ側でも対策する。ただし `LimitExceededException` や `TooManyRequestsException` は明示的にユーザーに伝える。

#### ステップ2のAPI呼び出し（リセット実行）

```
[パスワードをリセット] タップ
    ↓
Cognito SDK confirmForgotPassword({
  Username: <email>,
  ConfirmationCode: <6桁>,
  Password: <新パスワード>
})
    ↓
成功: ステップ3（完了画面）へ遷移
失敗: 上部にエラーバナー表示（後述）
```

#### コード再送

```
[コードを再送] タップ
    ↓
Cognito SDK forgotPassword({ Username: <email> })  // 同じAPIを再呼び出し
    ↓
成功: トースト `success`「コードを再送しました」、再送タイマーを60秒再開
失敗: トースト `error`「再送に失敗しました」
```

- 60秒タイマー中はリンク非活性、残り秒数を表示
- `LimitExceededException` が返ったら、トーストではなく上部エラーバナーで「しばらく時間をおいて…」を表示

#### 「変更」リンク（メールアドレスを直す）

- ステップ2で `変更` リンクタップ時、確認ダイアログ:
  - タイトル: 「メールアドレスを変更しますか？」
  - 本文: 「これまでに送信されたコードは無効になります」
  - ボタン: `キャンセル` / `変更する`
- 「変更する」でステップ1に戻る
  - メールアドレス欄に直前の値をプリセット（修正しやすく）
  - コード・パスワード入力欄はクリア

#### 戻るボタン操作

- ヘッダー左 `←` タップ、またはOSの戻るジェスチャー
- ステップ1の場合: 確認なしで S-005 へ戻る（入力途中保存の概念がないため、S-005 と同じ方針）
- ステップ2の場合: 確認ダイアログ表示
  - タイトル: 「パスワードリセットを中断しますか？」
  - 本文: 「中断すると、送信されたコードは無効になります」
  - ボタン: `続ける`（キャンセル）/ `中断する`（破壊的、赤）
  - 「中断する」で S-005 へ
- ステップ3の場合: 確認なしで S-005 へ戻る（既にリセット完了済み）

### 📡 データ・API

このページは **バックエンドAPIを呼ばず、Cognito SDKを直接呼び出す**（S-002 / S-005 と同じ方針）。

#### ステップ1: コード送信

```
Cognito SDK forgotPassword({
  Username: <email>
})
```

- 成功時のレスポンスには `CodeDeliveryDetails`（送信先メール・配送方法）が含まれる
- UI 上はメールアドレスをステップ2のヘッダーに表示するため、入力値をそのまま使えばよい

#### ステップ2: リセット実行

```
Cognito SDK confirmForgotPassword({
  Username: <email>,
  ConfirmationCode: <6桁>,
  Password: <新パスワード>
})
```

- 成功時のレスポンスは空（HTTP 200 のみ）
- 完了後、自動ログインはしない（前述の設計判断参照）

### 🌀 状態

| 状態 | 表示 |
|------|------|
| `request_default` | ステップ1、メール欄に値あり/なし、`コードを送信` ボタン状態に応じる |
| `request_valid` | ステップ1、メール形式OK、送信ボタン活性 |
| `request_submitting` | ステップ1、送信ボタンスピナー、入力ロック |
| `confirm_default` | ステップ2、コード未入力、リセットボタン非活性 |
| `confirm_entering` | ステップ2、コード入力中またはパスワード入力中、リセットボタン非活性 |
| `confirm_valid` | ステップ2、全項目バリデーション通過、リセットボタン活性 |
| `confirm_submitting` | ステップ2、リセットボタンスピナー、入力ロック |
| `done` | ステップ3、成功表示 |
| `error` | 上部エラーバナー、入力は保持 |
| `locked` | 試行回数/送信回数の上限到達、ボタン非活性 + 案内 |

### ⚠️ エッジケース

#### 入力エラーの表示

- エラー項目の **直下に赤字メッセージ**（12px / `color/danger`）
- 該当項目の枠線も赤に変わる
- ボタンはエラー解消まで非活性

#### Cognitoエラー（ステップ1: forgotPassword）

| エラーコード | 表示メッセージ | 動作 |
|-------------|--------------|------|
| 成功 / `UserNotFoundException` | （エラーメッセージ表示なし） | **どちらもステップ2へ遷移**（ユーザー列挙攻撃対策） |
| `InvalidParameterException` | 「メールアドレスの形式が正しくありません」 | メール欄にインラインエラー |
| `LimitExceededException` | 「送信回数の上限に達しました。しばらくしてからお試しください」 | エラーバナー、ボタンを15分間非活性 |
| `TooManyRequestsException` | 「しばらく時間をおいて再度お試しください」 | エラーバナー、ボタン10秒非活性 |
| `NotAuthorizedException`（リセット不能ユーザー） | 「このアカウントではパスワードリセットができません。サポートへお問い合わせください」 | エラーバナー（Google経由ユーザーや管理者無効化アカウント） |
| `CodeDeliveryFailureException` | 「コードの送信に失敗しました。しばらくしてからお試しください」 | エラーバナー、再試行可 |
| `NetworkError` / その他 | 「送信に失敗しました。通信状況をご確認ください」 | エラーバナー、再試行可、入力は保持 |

#### Cognitoエラー（ステップ2: confirmForgotPassword）

| エラーコード | 表示メッセージ | 動作 |
|-------------|--------------|------|
| `CodeMismatchException` | 「コードが正しくありません」 | コード欄を赤枠 + クリア、フォーカスを先頭に戻す。残り試行回数を表示（後述） |
| `ExpiredCodeException` | 「コードの有効期限が切れました。再送してください」 | 上部エラーバナー、リセットボタン非活性、`コードを再送` を強調表示 |
| `InvalidPasswordException` | 「パスワードがポリシーを満たしていません」 | パスワード欄にインラインエラー（通常はクライアント側で防げるはず） |
| `LimitExceededException` / `TooManyFailedAttemptsException` | 「試行回数が上限に達しました。しばらくしてからお試しください」 | `locked` 状態へ、リセットボタンと再送リンクを15分間非活性 |
| `UserNotFoundException` | 「ユーザーが見つかりません。最初からやり直してください」 | エラーバナー + ステップ1へ戻るボタン |
| `InvalidParameterException` | 「入力内容に誤りがあります」 | 上部エラーバナー |
| `NetworkError` / その他 | 「リセットに失敗しました。通信状況をご確認ください」 | エラーバナー、再試行可、入力は保持 |

#### 残り試行回数の表示

S-003 と同じ方針：

- `CodeMismatchException` 発生時、エラーメッセージに残り回数を添える
  - 例: `コードが正しくありません（残り 2 回）`
- 5回連続失敗で `locked` 状態へ
- 残り回数はクライアント側でカウント（Cognito からは直接返らない想定）

#### コード期限切れ

- Cognito の `forgotPassword` 検証コードは標準で **1時間** 有効
- UI 上は短めに `15分` のソフト期限カウントダウンを表示（S-003 と同じ方針）
- ソフト期限切れ：
  - リセットボタン非活性
  - コード入力欄は薄く `disabled` 表示
  - `コードを再送` を `color/primary` に強調
- ハード期限（1時間）切れの場合は `ExpiredCodeException` で対応

#### メールが届かない

S-003 と同じ案内：

- 「メールが届かない場合」のヘルプテキストを表示
- 主な原因として案内:
  - 迷惑メールフォルダの確認
  - メールアドレスの誤入力 → `変更` リンクからステップ1へ戻る
  - ドメイン受信設定（`@example.com` を許可）
  - そもそも登録されていない可能性（ただし明示しない、列挙対策のため）
- `コードを再送` を試してもらう（60秒制限あり）

#### Googleユーザーがパスワードリセットを試行

- Cognito 側で Google IDプロバイダ経由のユーザーは、`forgotPassword` を呼んでも対応するパスワードが存在しないため、`NotAuthorizedException` が返る想定
- 上記表のメッセージで「サポートへお問い合わせください」を案内
- ステップ1の入力欄下の info カードで事前にも警告（前述）

#### パスワード貼り付け・自動入力

- パスワードマネージャー連携を妨げないため、貼り付けは許可
- `autocomplete=new-password` を指定して、ブラウザ・パスワードマネージャーへの新規保存を促す

#### 多重サブミット

- `submitting` 状態ではボタン・入力欄をすべて非活性
- ダブルタップでの二重リクエストを防ぐ

#### オフライン時

- Cognito SDK 呼び出しはタイムアウト → エラーバナー「オフラインです。接続後に再度お試しください」
- フォーム入力は保持

#### 既ログインユーザーが `/password-reset` に直接アクセス

- ルートガードでは弾かない（パスワード変更したいケースもある）
- ただし、ログイン済みユーザーには「すでにログイン中です。パスワードを変更するには 設定 → アカウント へ」というinfoバナーを画面上部に表示
- 操作自体は通常通り可能

#### ステップ間の state 保持

- リロード（F5）したらステップ1からやり直し（state はメモリ保持のみ、URL に載せない）
- 理由: コードはメールに記載されているため、リロードしても継続できる必要がない & セキュリティ上 URL に載せたくない

#### 「パスワードを忘れた」からの遷移時のメール引き継ぎ

- S-005 から遷移時、メールアドレスを state で受け取る（URLパラメータでは受け取らない、S-003 と同じ方針）
- ステップ1のメール欄に自動入力 + フォーカス（あとは「コードを送信」ボタンを押すだけの状態）

### 💭 設計判断メモ

| 判断 | 理由 |
|------|------|
| Cognito SDK を直接呼ぶ（API経由でない） | S-002 / S-005 と統一。Cognito の責務範囲なので EC2 を経由する意味がない |
| 2ステップを1画面内で切り替え | URL を変えずに state で切り替えることで、リロード時のセキュリティリスクを下げ、ブラウザ履歴も汚さない |
| `UserNotFoundException` でも成功と同じ挙動 | ユーザー列挙攻撃対策。S-005 の `NotAuthorized` / `UserNotFound` 同一文言と同じ思想 |
| 新パスワードのチェックリストを表示 | S-002 と統一。新規パスワードを決める場面なので可視化が有効 |
| ステップ2でメールアドレスを上部表示 + 変更リンク | S-003 と統一。誤入力の救済導線 |
| 完了後に自動ログインしない | 安心感を与え、攻撃者の即時侵入を一段防ぐ。Cognito API 仕様上も追加実装を避けられる |
| state（メールアドレス）は URL に載せない | S-003 / S-005 と同じセキュリティ方針 |
| 認証系画面で BottomNavigation 非表示 | screens.md の共通仕様に準拠 |
| 既ログインユーザーも操作可能 | 設定画面からのパスワード変更導線も将来この画面に集約する可能性がある |
| ステップ1の戻るは警告なし | 入力途中保存の概念がないため、確認ダイアログは煩わしい（S-005 と同じ方針） |
| ステップ2の戻るは警告あり | コードがメールに残るため「中断するとコードが無効になる」ことを伝える価値がある |
| 再送制限60秒 | S-003 と統一。サーバ側の `LimitExceededException` を防ぐクライアント側のガード |
