## S-005 ログイン

**URL**: `/login`
**Figma**: [{TBD}]({TBD})

### 🎯 目的

- 既存ユーザーが、最短ルートでログインできるようにする
- 「メール+パスワード」と「Google」の2経路を1画面で提示し、好きな方を選べる設計にする
- パスワード忘れ・未確認ユーザー・誤ったメールアドレスなど、ログインで詰まりやすいケースに自然に誘導する

### 📋 構成要素

#### ヘッダー（上部固定、56px / 共通仕様準拠）

| パーツ | 配置 | 内容 |
|-------|------|------|
| `←` 戻る | 左 | S-001 スプラッシュへ戻る |
| タイトル | 中央 | `ログイン` |
| (右はアイコンなし) | 右 | - |

> 認証系画面のため BottomNavigation は非表示。

#### イントロブロック（ヘッダー直下）

- 大きめの見出し: `おかえりなさい`（h1相当、24px / 700）
- サブテキスト: `メールアドレスまたはGoogleアカウントでログインできます`（text/body、`color/text-secondary`）
- 下に余白24px

> **設計判断**: 「ログイン」ではなく「おかえりなさい」と表現することで、再訪ユーザーへの親しみを出す。S-002 の `アカウントを作成` と対になる文言。

#### Googleでログインブロック

- ボタン1つ：`Googleでログイン`（Button `lg`、横幅100%、白背景 + 1px border、左にGoogleロゴ20px）
- タップで Cognito Hosted UI（Google IDプロバイダ指定）へリダイレクト
- 認証後は `/api/me` 経由で S-101 ホームへ直接遷移（MFAなし）

#### 区切り

- 横線 + 中央に「または」（text/caption、`color/text-secondary`、線の色 `color/border`）
- 上下に余白16px

#### フォーム本体（縦スクロール）

##### 入力フィールド

| フィールド | 入力UI | 仕様 |
|-----------|-------|------|
| メールアドレス ※ | Input `text`（type=email） | 1〜254文字、メール形式、`autocomplete=email`、`inputmode=email` |
| パスワード ※ | Input `text`（type=password、目アイコンで表示切替） | 入力必須（具体的なポリシーチェックはここでは行わない）、`autocomplete=current-password` |

##### パスワード欄下の補助リンク

- 右寄せに `パスワードを忘れた` リンク（`color/primary`、text/caption）
- タップで S-007 パスワードリセットへ
  - メールアドレス欄に値があれば、それをプリセットして引き継ぐ

> **設計判断**: S-002 と異なりパスワードポリシーのチェックリストは出さない。既存ユーザーは「自分のパスワード」を打つだけで、ポリシー違反の指摘は不要かつ煩雑。サーバ側のエラーで対応する。

#### ボトム固定フッター（72px / 共通仕様準拠）

- `ログイン` ボタン（Button `lg` primary、横幅100%、高さ48px）
  - メール・パスワードの両方が入力されるまで非活性
  - タップでローディング状態へ（スピナー表示、入力ロック）

#### フッター直下

- 補助リンク: `アカウントをお持ちでない方は 新規登録`
  - 「新規登録」部分が `color/primary` のリンク、タップで S-002 へ
  - text/body (16px)、中央寄せ

### 🔄 インタラクション

#### バリデーションのタイミング

S-002 / S-003 と同じ方針：

- **初回フォーカス前はエラー表示しない**
- blur 以降からインラインバリデーション開始
- フォーマット系のエラー（メール形式不正等）はクライアント側で判定、認証失敗はサーバ側で判定

#### バリデーションルール（クライアント側）

| 項目 | ルール | エラーメッセージ例 |
|------|--------|------------------|
| メールアドレス | RFC準拠メール形式、1〜254文字 | 「メールアドレスの形式が正しくありません」 |
| パスワード | 入力必須（文字数等はチェックしない） | 「パスワードを入力してください」 |

#### パスワード表示切替

- パスワード欄の右端に目アイコン（24×24px）
- タップで `type=password` ↔ `type=text` を切替
- ログイン画面では「確認用」がないので1つだけ

#### ログイン経路ごとの遷移

```
[ログイン] タップ
    ↓
Cognito SDK initiateAuth({
  AuthFlow: "USER_PASSWORD_AUTH",
  AuthParameters: { USERNAME: <email>, PASSWORD: <password> }
})
    ↓
レスポンスの ChallengeName により分岐:
  - SOFTWARE_TOKEN_MFA   → state(session) を持って S-006 へ
  - MFA_SETUP            → state(session) を持って S-004 へ（MFA未設定ユーザー）
  - NEW_PASSWORD_REQUIRED → S-007 へ（管理者リセット直後など、稀ケース）
  - AuthenticationResult が直接返る → 後述「Googleユーザーの直接ログイン」参照
失敗: エラーバナー表示（後述）
```

> **設計判断メモ**: 通常のメール認証ユーザーは MFA 必須のため、`initiateAuth` 直後は必ず `SOFTWARE_TOKEN_MFA` チャレンジが返る前提。`MFA_SETUP` は「メール確認は済んでいるが S-004 を完了していないユーザー」がログイン試行した場合のリカバリー導線となる。

#### Googleでログインのフロー

```
[Googleでログイン] タップ
    ↓
Cognito Hosted UI へリダイレクト（identity_provider=Google）
    ↓
Google ログイン画面（既ログインならスキップ）
    ↓
コールバックURL（/auth/callback）に戻る
    ↓
GET /api/me（JIT取得 / 作成）
    ↓
S-101 ホーム
```

- Google経路は MFA を Google 側に委譲するため、S-006 は経由しない
- 初回ログイン時は `/api/me` で JIT 方式によりバックエンド側に `users` レコードを作成（design.md §1.6）

### 📡 データ・API

このページは **バックエンドAPIを呼ばず、Cognito SDKを直接呼び出す**。

```
Cognito SDK initiateAuth({ AuthFlow: "USER_PASSWORD_AUTH", AuthParameters: {...} })
```

- `username` (= メールアドレス) と `password` を Cognito SDK に渡す
- 成功時の session / ChallengeName を state で次画面に引き継ぐ
- 完了後の `/api/me` は次画面（S-006 など）の責務

#### Googleでログインの場合

- 直接APIは叩かず、Cognito Hosted UI へのリダイレクトのみ
- リダイレクトURL: `{Cognito Domain}/oauth2/authorize?identity_provider=Google&...`

### 🌀 状態

| 状態 | 表示 |
|------|------|
| `default` | 通常フォーム、ログインボタン非活性 |
| `valid` | メール・パスワード入力完了、ログインボタン活性 |
| `submitting` | ログインボタンスピナー、フォーム入力ロック、Googleボタンも非活性 |
| `success` | （遷移するため UI上は表示しない、即 S-006 / S-004 / S-101 へ） |
| `error` | 上部エラーバナー表示、フォームは保持、再送信可能 |
| `locked` | アカウントロック状態、ボタン非活性、案内表示 |

### ⚠️ エッジケース

#### 入力エラーの表示

- エラー項目の **直下に赤字メッセージ**（12px / `color/danger`）
- 該当項目の枠線も赤に変わる
- ログインボタンはエラー解消まで非活性

#### Cognitoエラー

| エラーコード | 表示メッセージ | 動作 |
|-------------|--------------|------|
| `NotAuthorizedException` | 「メールアドレスまたはパスワードが正しくありません」 | 上部エラーバナー、入力は保持（パスワード欄はクリアしない方針） |
| `UserNotFoundException` | 「メールアドレスまたはパスワードが正しくありません」 | 上部エラーバナー（**`NotAuthorizedException` と同一文言**で、ユーザー存在の有無を漏らさない） |
| `UserNotConfirmedException` | 「メール確認が完了していません。確認コードを再送します」 | エラーバナー + 自動的に `resendConfirmationCode` を呼び、S-003 へ遷移（メールアドレスを state で引き継ぎ） |
| `PasswordResetRequiredException` | 「パスワードのリセットが必要です」 | 上部エラーバナー + `パスワードリセットへ` ボタン併設 → S-007 へ |
| `InvalidParameterException` | 「入力内容に誤りがあります」 | 上部エラーバナー |
| `LimitExceededException` / `TooManyFailedAttemptsException` | 「ログイン試行回数が上限に達しました。しばらくしてからお試しください」 | `locked` 状態へ、ログインボタンを15分間非活性 |
| `TooManyRequestsException` | 「しばらく時間をおいて再度お試しください」 | エラーバナー、ボタン10秒非活性 |
| `NetworkError` / その他 | 「ログインに失敗しました。通信状況をご確認ください」 | エラーバナー、再試行可、入力は保持 |

> **設計判断メモ（セキュリティ）**: `UserNotFoundException` と `NotAuthorizedException` で **同一の文言を返す**。これにより、攻撃者が「そのメールアドレスが登録されているか」を判別できなくする（ユーザー列挙攻撃対策）。Cognito 側でも User Pool 設定で `Prevent user existence errors` を有効化することで同様の挙動になるため、サーバ側設定とクライアント側文言の両方で対応する。

#### 未確認ユーザー（UserNotConfirmedException）

- 「メール確認を済ませていないユーザー」がログインに来た場合の救済導線:
  - エラーバナーに `確認コードを再送して続ける` ボタンを併設
  - タップで `resendConfirmationCode` を呼び、成功したら S-003 へ遷移（メールアドレスを引き継ぎ）
  - 失敗時はトーストでエラー表示

#### Googleユーザーがメールフォームで試行

- Cognito側に Google経由で作られたユーザーは、メール+パスワードのフォームではログインできない
- 通常は `NotAuthorizedException` が返るため、上記と同じ文言を表示
- ヒントとして、エラーバナー下に `Googleで登録した場合は「Googleでログイン」をお試しください` を小さく添える

#### アカウントロックアウト

- Cognito 標準では5回連続失敗で一時ロック（design.md §1.8 参照）
- `locked` 状態時の表示:
  - 「ログイン試行回数が上限に達しました」エラーバナー
  - 「15分後に再度お試しいただくか、パスワードリセットをご利用ください」案内
  - `パスワードリセットへ` ボタン併設 → S-007 へ
  - 入力欄は disabled、ログインボタンも非活性

#### パスワード貼り付け・自動入力

- パスワードマネージャー連携を妨げないため、貼り付けは許可
- `autocomplete=current-password` を指定して、ブラウザ・パスワードマネージャーの自動入力に対応

#### 「パスワードを忘れた」リンク

- メールアドレス欄に値がある場合 → そのメールアドレスを state で引き継いで S-007 へ
- 空の場合 → S-007 で空フォームから始まる
- 引き継ぎは URL パラメータではなく state で行う（メール漏洩防止、S-003 と同じ方針）

#### Googleでログイン時に途中キャンセル

- Cognito Hosted UI 上でキャンセル → 元の S-005 に戻る
- フォーム入力内容は保持されない（リダイレクト跨ぎのため）
- エラーメッセージは表示しない（ユーザー意図のキャンセル）

#### 入力済みで戻るボタンを押した場合

- ヘッダー左 `←` タップ、またはOSの戻るジェスチャー
- メール・パスワードがどちらも空 → 警告なしで S-001 へ
- 何か入力済み → 警告なしで戻る（S-002 と挙動を変える）
  - 理由: ログインフォームは「入力途中の保存」の概念がないため、確認ダイアログは煩わしい
  - パスワードはクリアされても再入力で済む（パスワードマネージャーがあるなら一瞬）

#### オフライン時

- Cognito SDK 呼び出しはタイムアウト → エラーバナー「オフラインです。接続後に再度お試しください」
- フォーム入力は保持

#### 多重サブミット

- `submitting` 状態ではログインボタン・Googleボタン・入力欄をすべて非活性
- ダブルタップでの二重リクエストを防ぐ

#### 既ログインユーザーが `/login` に直接アクセス

- ルートガードで判定し、ログイン済みなら `/home` へ自動リダイレクト
- S-001 / S-002 と同じ挙動

### 💭 設計判断メモ

| 判断 | 理由 |
|------|------|
| Cognito SDK を直接呼ぶ（API経由でない） | S-002 と統一。Cognito の責務範囲なので EC2 を経由する意味がない |
| Googleボタンを最上部に配置 | S-002 と統一。多くのユーザーが Google アカウントを持つ前提 |
| メール経路とGoogle経路を1画面に集約 | S-002 と統一。経路選択を分かりやすく |
| パスワードポリシーのチェックリストは出さない | 既存ユーザーには不要かつ煩雑。サーバエラーで対応 |
| `UserNotFound` と `NotAuthorized` を同一文言に | ユーザー列挙攻撃対策（タイミング攻撃対策はサーバ側で別途） |
| パスワード入力失敗時にフィールドをクリアしない | 「打ち直すだけ」のケースが多いため、保持の方がUX良。タイポ修正もしやすい |
| `UserNotConfirmedException` は自動で S-003 へ救済 | 未確認ユーザーが詰まる典型ケースを最短で救う |
| `PasswordResetRequiredException` 時にリセット導線併設 | 管理者リセット直後など稀ケースのフォロー |
| 「パスワードを忘れた」で入力済みメールを引き継ぎ | 二度入力させない |
| state（メールアドレス）は URL に載せない | S-003 と同じセキュリティ方針 |
| ログイン画面の戻るは警告なし | 入力途中保存の概念がないため、確認ダイアログは煩わしい |
| `autocomplete=current-password` 指定 | パスワードマネージャー連携を積極活用、認証速度向上 |
| 認証系画面で BottomNavigation 非表示 | screens.md の共通仕様に準拠 |
| 「おかえりなさい」の文言 | S-002 の「アカウントを作成」と対比、温かみのある印象 |
